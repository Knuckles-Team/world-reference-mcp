# World Reference MCP Development

Use this skill when changing the `world-reference-mcp` connector, its documentation,
or its spec-delivery integration. Work from the repository root and read `AGENTS.md`,
the affected module, and the relevant `specs/` status before editing. Keep vendor
calls behind the existing MCP tools and SDK source adapters, with credentials resolved
server-side.

## Steps

1. Read `AGENTS.md` and find the owning spec row with `git grep -n "<term>" -- specs`. Verify one row owns the change.
2. Name the files the change touches with `git status --short` after editing. Verify only those files are modified.
3. Run the narrowest mocked test with `uv run pytest -q tests/<test file>`. Verify it passes without network or credentials.
4. Run the repository hooks with `pre-commit run --all-files`. Verify every hook reports Passed.
5. Review the full diff with `git diff`. Verify no credentials, raw vendor responses or generated output are present.

## Failure recovery

| Failure | Cause | Recovery |
|---------|-------|----------|
| Test reaches the network | Vendor call not mocked | Patch the adapter call in the test and rerun the single test file |
| Pre-commit hook rewrites files | Formatter or spelling hook applied fixes | Stage the rewritten paths with `git add -- <path>` and commit again |
| Spec status file changed by hand | Status is generated | Restore it with `git checkout -- <path>` and let the pipeline tool regenerate it |

## Rapid delivery: the 5-minute contract

For a small, reviewable change:

1. Identify one requirement or maintenance slice and name the exact files it touches.
2. Reuse the existing vendor adapters, SDK, central pipelines, and package conventions.
   Do not add a second transport, graph client, planner, publisher, or CI framework.
3. Keep spec status generated by the canonical pipeline tools. Run the narrowest
   relevant test, then run `pre-commit run --all-files` from the repository root.
4. Review the complete diff, including workflow and package-data changes, and record
   the source revision plus the commands and results used as evidence.
5. Keep credentials, raw vendor responses, generated output, caches, and scratch files
   outside the checkout. A Pages claim is complete only after the central reusable
   workflow has run and the exact published `spec-delivery/` source is checked.

### Change boundaries

- Preserve the existing MCP tools, bounded HTTP pacing, SDK source adapters, and
  server-side credential references.
- Treat the world-reference vocabulary mappings and existing world-model ontology as
  connector-owned contracts; extend them only when the requirement explicitly calls
  for a mapping change.
- Keep the declarative source presets and runtime schemas aligned with the existing
  adapter contracts rather than adding a parallel ingestion path.
- Use the central Pages workflow and `.config/spec-dashboard.json` for the spec
  dashboard; keep one documentation publisher for this repository.
- Keep the central aggregate hooks in `.pre-commit-config.yaml`; do not copy their
  implementation or create a second CI framework.

### Validation evidence

For code changes, run the narrowest relevant mocked test first and then the repository
hooks. For delivery changes, validate JSON and YAML syntax and inspect the rendered
dashboard inputs before requesting review. Report failures with the command, revision,
and file or line that needs attention; do not hide a failing check behind a skipped
hook.
